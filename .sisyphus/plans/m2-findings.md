# M2-a Findings

## Approval gate edge cases

- The hold predicate is conjunctive: git handoff, a roster role literally named `specifier`, sender is the roster's `worktree=master` role, exactly one recipient, and no `approved: true` header.
- Notes and broadcasts remain immediate delivery paths, including when sent by the master role in a specifier roster.
- Rosters without a `specifier` retain M0 immediate-delivery behavior.
- Approved files enter through the project-root outbox; the parsed `approved: true` lifecycle field prevents re-holding after restart.
- Approval IDs are resolved from parsed pending files rather than inferred from filenames.

## Batch resume assumption

- A batch directory is the durable dequeue boundary. Every member is moved into that directory and stamped with `dequeued_at` before any merge starts.
- On restart, an existing `batch_*` directory is returned as `BATCH` without re-running merges. This follows the M0 resume convention and assumes merges completed before the process interruption; it intentionally favors idempotency over trying to infer partial merge progress.
- A merge conflict leaves every member in the same batch directory and reports the complete filename list in the structured error.

## Clarification IDs

- IDs use `clar-<compact UTC timestamp>-<six digit process-local sequence>`, for example `clar-20260824T010203Z-000000`.
- Request filenames append `.request`; request content is `role: <role>`, a blank line, then the question verbatim.
- The current `@deepseek-ai/dsh-tools` value-schema DSL rejects `maxLength`. The 500-character limit is therefore enforced by `SwarmForgeService.submitClarification`, keeping the host contract authoritative without a type shim or dependency change.

Matches `packages/goal/goal/src/index.ts:204-213`'s pattern exactly: guarded by `ctx.inject(['sessionProjections'], cb)` so a headless assembly without the registry stays unaffected (`src/projection/register.ts`). ## Build-chain decisions

- **Two independent tsconfigs.** `tsconfig.json`/`tsconfig.build.json` (host, untouched, glob `src/**/*.ts`) never sees client code because **every** client source file uses a `.tsx` extension, including files with zero JSX (`src/client/commands.ts` is the one exception — pure, no browser-only imports, safe under the strict host program and intentionally left `.ts` so it is also host-typechecked/built harmlessly; `src/client/projection.ts` similarly stays `.ts` since it only takes type-only imports). `src/client/index.tsx` and `SwarmTab.tsx` are `.tsx` specifically so the `src/**/*.ts` glob cannot pull them in — empirically verified: a `.ts` file importing a `.tsx` file breaks `tsc -p tsconfig.build.json` with `TS6142 ... '--jsx' is not set`, confirmed with a throwaway probe before committing to this layout. `tsconfig.client.json` (new, host-adjacent, not forbidden) covers `src/client/**/*.{ts,tsx}` with `jsx: react-jsx`, DOM lib, `moduleResolution: Bundler`, and `allowImportingTsExtensions: true` (required because `SwarmTab.tsx` is imported by its literal extension, matching the exact `ui-trajectory` import convention `from './TrajectoryView.tsx'` under the harness's own Bundler-resolution client tsconfig).
- **`build:client` is a separate script, not chained into `build`.** Per the task's own gate (`pnpm typecheck && pnpm test && pnpm build && pnpm build:client`) and "keep host build untouched", `package.json#scripts.build` stays exactly `tsc -p tsconfig.build.json`. `build:client` = `tsc -p tsconfig.client.json --noEmit && tsdown` (type-check, then bundle).
- **`tsdown.config.ts`** (root, since this package is not a deepseek-harness workspace member and has no access to the monorepo's shared `packages/client/tsdown.client.ts` preset) hand-rolls the minimal equivalent: `entry: 'src/client/index.tsx'`, `platform: 'browser'`, `format: 'esm'`, `outDir: 'dist'`, `outputOptions.entryFileNames: 'client.js'`, **`clean: false`** (load-bearing — `dist/` is shared with the host `tsc` build's `index.js`/`index.d.ts`; tsdown's default `clean: true` would delete them), `dts: false` (no published type declarations for `./client`, matching the task's "keep it minimal").
- **React is bundled into `client.js`, not externalized.** The harness's real `ui-trajectory` bundles against a host-provided module table (`PLATFORM_MODULES`/`PRELOADED_CLIENT_EXTERNALS` in `packages/client/web/src/platform.ts`, private to that monorepo) so `react` resolves to a shared host copy at runtime. This package has no access to that mapping and cannot verify the exact module id the real `dsh` web host would supply, so it takes the safe, self-contained default: `react`/`react-dom` are plain devDependencies (not `dependencies`/`peerDependencies`), so tsdown's default dependency-bundling policy inlines them. Verified: `pnpm build:client` output logs `Detected dependencies in bundle: - react` and produces one 97.69 kB `dist/client.js` (gzip 22.53 kB). Tradeoff: larger artifact than the upstream convention, no risk of resolving a mismatched host React instance. Documented as a candidate M3 optimization if this package is ever vendored into a monorepo that exposes its module table.
- **No locale package.** `dsh-client-ui-slots`' `locale` field on `register()` is optional (`BaseOptions.locale?: N`, confirmed in `lib/types/index.d.ts:422-428`); per the task's own "UI text English" constraint we use a plain string label (`'Swarm'`) and skip `@deepseek-ai/dsh-client-locale` entirely — one fewer dependency, no dictionaries to maintain for an English-only M2 panel. `@deepseek-ai/dsh-client-locale` was installed to inspect the pattern, found unused, and removed again.
- **`SwarmQueueSnapshot`'s array fields are `readonly <field>: T[]` (property-readonly, element-mutable), not `readonly T[]`.** `ProjectionDefinition.apply` must return a value assignable to the zod-inferred state type, and zod's plain `z.array(...)` output is a mutable-element array; a `readonly T[]`-typed return is not assignable to that mutable slot. Kept the outer property `readonly` (assignment-safety) and the array itself mutable to match zod's inferred shape without adding `.readonly()` schema calls.

## `conversation.view` scope choice (per §6 context)

Approvals/clarifications are swarm-global, not per-session, but the projection lives on the coordinator session's own log (there is nowhere else to append a durable event). `src/client/projection.ts`'s `resolveSwarmProjection(current, sessions)` implements exactly the documented M2 simplification: prefer the *current* session's own `useProjection('swarm')` value when it is non-null; otherwise scan `useSessions()`'s `SessionListState.byId[...].projectionValues.swarm` (a documented whole-value map published per session summary specifically so "global list consumers... reuse the same projections without creating per-session subscriptions" — `dsh-client-runtime` README) for the first session carrying a non-null swarm snapshot; otherwise `undefined` → "Swarm not started". This is a pure function with full unit coverage (`test/client/projection.test.ts`) and does not require a new host API.

## What needs manual browser verification

This package cannot run inside deepseek-harness's actual web host from this repo (no browser automation was used, per task constraints; only build + unit tests were run). The following are unverified beyond type-level and unit-test confidence and should be checked by hand once this bundle is loaded into a real `dsh` web assembly:

1. **`window.__ModuleLoader__` wire compatibility.** The real harness bundles wrap client artifacts in a `window.__ModuleLoader__.load({ id, factory: (require) => {...} })` banner/footer (`packages/client/tsdown.client.ts`), which our hand-rolled `tsdown.config.ts` does **not** reproduce (plain ESM `format: 'esm'` output instead, per the task's literal "output dist/client.js ESM" instruction). Whether the actual `dsh` web host's module loader accepts a plain ESM module at `exports['./client']` or specifically requires the CJS-factory wire convention is unverified — this is the single highest-risk item for real integration and needs a manual load-in-browser check.
2. **Slot render smoke test**: that the "Swarm" tab actually appears in the conversation view tab strip at the expected position, that Approve/Reject buttons call through to the host `/swarm approve|reject <id>` command and the tab re-renders from the resulting `session/projection` push frame, and that the Clarify answer input clears on success.
3. **Cross-session fallback in practice**: opening a non-coordinator session (e.g. one of the spawned role's own anchor session, if it is ever visible in the session list) and confirming the Swarm tab still shows the coordinator's live queue via the `useSessions` fallback, per the scope decision above.
4. **Bundle size** (97.69 kB / 22.53 kB gzip) in a real page load — acceptable for M2, flagged above as an M3 candidate for optimization if a shared React module ever becomes available to this package.
